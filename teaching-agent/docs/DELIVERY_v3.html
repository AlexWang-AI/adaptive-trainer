二、红蓝对抗：三轮真机才发现的问题

这些都是「单元测试全绿、一上浏览器就露馅」的类型。
#蓝方（我写的）红方（真机打脸）修法
1讲练节点注册了流式 sink建图时 session_id 没传给 initial_state，新会话 id 与 sink 的 key 对不上 → 一个 content 事件都没有把 session_id=sid 传进去
2流式提取器能「边收边解析」markdown遇到收尾引号后没封口，后续 chunk 继续被吞 → 讲义末尾混进整段 JSON（截图里能看到 "questions":[{...）加 _finished 闸门，见到收尾引号立即停
3Next 代理直接透传 upstream.bodyNext 默认压缩把 SSE 缓冲成批，后端 1.9 s 的首字到浏览器变 5.8 snext.config.mjs 关 compress，并加 allowedDevOrigins
4输出上限设 2200 token讲义 + 3 题卡偶尔超长被截断，JSON 不合法 → 整轮重生成，客户端首字从 1.5 s 变 18 s上限提到 3200；trace 里 attempts 从 2 回到 1
5边跑 next build 边验收构建进程吃掉一核 CPU，dev server 被拖慢，TTFT 全部 8~18 s验收前先停构建；写进交付说明
6用 next dev 交付Turbopack 开发服务器对长连接 SSE 的转发不稳，同一份代码首字在 1.4~15 s 之间抖预热路由 + 稳定后实测 1.8~2.0 s；启动脚本会在有构建产物时优先 npm run start
7每次启动都让 Next 跑 Tailwind/PostCSS本机 Tailwind v4 单次编译要 5~6 分钟，Turbopack 的 postcss loader 子进程直接超时 → 页面 500、build 失败（这就是上一轮「打不开」的真因，不是内存）改成预编译 CSS：scripts/build_css.mjs 一次性生成 app/prebuilt.css，并停用 postcss.config → 页面编译从 6 分钟降到 6 秒

第 3 条尤其隐蔽：后端日志显示 handler 12 ms 就拿到 upstream 头，但客户端 4.4 s 才收到响应头——问题不在业务代码，在框架默认行为。

四、怎么启动 / 怎么自测

一键启动
双击项目根目录的 start_all.bat

或 PowerShell：
powershell -ExecutionPolicy Bypass -File scripts/start_all.ps1

首次使用（还没构建）：
npm run build   # 约 3 分钟，之后启动脚本会自动走生产模式

脚本会拉起 Python 后端（8008）与 Next 前端（3000），等健康检查通过后自动打开浏览器。

自动化验收
# 接口级（模拟前端，走 Next 代理）
python scripts/check_e2e.py

# 浏览器级（CDP 真机点击 + 答题 + 截图）
node scripts/browser_smoke.mjs

两者都是「任何一条不过就非零退出」，可以直接当回归门禁。

五、常见问题

现象原因与处理
页面一直「正在读取知识树…」后端没起或端口被占。先访问 http://127.0.0.1:8008/api/health_v3 看是否 200。
讲义不动、只有转圈看 8008 窗口是不是 402（余额）或 401（key）。v3 对这类错误是立即失败、不重试，避免把一次调用放大成三次。
清空进度重来删掉 backend/data/mastery.db 即可（只影响通关状态，不影响题库）。
换端口后端改 --port 后，在 .env.local 里设 AGENT_API_URL=http://127.0.0.1:新端口。

数据说明：TTFT 为 scripts/check_e2e.py 在 Next 代理链路上连打 4 次取中位数（首字到达浏览器前端的毫秒数；首次请求要等路由冷编译，约 3.9 s）； 「1 次 LLM 调用」来自后端 trace 的 node 事件计数；判题耗时来自 /api/judge 返回的 elapsed_ms。

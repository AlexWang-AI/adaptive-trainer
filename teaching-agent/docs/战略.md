# 战略.md — 项目架构白皮书（战略基线 v2.0）

> **性质**：全项目唯一战略基线。战略层由用户拍板；**战术层由 AI 自行探索并拍板**（见 S0）。
> **修改规则**：AI 不得擅自修改战略条目；只能"提议"，由用户批准后写入第 13 节变更记录。
> **执行规则**：**每一轮动手前必须先读本文件**，对照 S0–S12 与第 3、6、7 节的硬规则；发现漂移立即停下回到本文。
> 冻结：2026-11-06　v2.0 由用户指令升级（新增 S0 战术自主原则，并把"先批准再写代码"改为"AI 自定方案，用户只验收"）

## 0. 三条元规则（最高优先级，先于一切战略）

### S0-1 分工：用户管战略与验收，AI 管战术与执行

| 谁 | 负责 | 不负责 |
|---|---|---|
| **用户** | 提要求、定战略方向、**验收效果**、指出体验问题与信息缺口 | 不做技术选型、不定实现路径、不被要求"拍板" |
| **AI** | 检索 2026 现状 → 自己列出候选路径 → 自己选最优 → 自己执行 → 自己评测 → 效果不好自己换路 | 不擅自改战略；不把战术决策推给用户 |

**禁止**：再向用户提问"用 A 还是 B""要不要跑""选哪个格式"这类战术问题。用户已经明确：**方案由 AI 自己看哪条最优，AI 拍板。**

### S0-2 动手前必须走完「最优路径探索四步」

任何非平凡任务，执行前必须：

1. **检索**：查 2026 年截至当前（11 月）该问题的最前沿做法（官方文档/工程博客/论文/GitHub 现状），不靠记忆。
2. **列候选**：至少写下 2–3 条可行路径 + 各自的成本/风险/成熟度。
3. **小样本验证**：用最小代价（10 分钟以内、少页数、少样本）先验证关键假设，**不允许直接全量开跑**。
4. **选定并记录**：把"为什么选它"写进交付物备注；效果不好时回来换第 2 条候选。

### S0-3 结果导向：不好就换路，不硬扛

一条路径如果两个迭代内没有明确改善，**必须换路径**，并把"试过什么、为什么不行"记下来。禁止在同一条坏路径上反复微调 prompt。

## 2. 产品战略：我们到底在造什么

### 2.1 一句话

> 学生带着明确目标进来（"两周把极限学扎实"），系统给一条能执行、能量化、能验收的路径，每一步告诉他"现在做什么、离掌握还差多少"，直到他能**独立做出教辅原题 + 独立做出同构变式题**。

不是聊天机器人，不是题库。核心交付物是**"掌握"这个判定**。

### 2.2 掌握判定（全项目唯一口径）

| 条件 | 判定方式 | 证据来源 |
|---|---|---|
| 独立做对 ≥2 道教辅原题 | 学生作答 + 判分 | `quiz` + `judge` |
| 独立做对 ≥1 道同构变式 | 换数字/换形态，同考点 | `quiz`(变式) + `judge` |
| 步骤无卡顿、无提示 | 计时 + 判分记录 | `judge` |
| 综合单元：再做对 1 道综合题 | 跨知识点、对标考研难度 | `exam` + `judge` |

```
kp.mastery = 0.4×min(独立对/2,1) + 0.4×min(变式对/1,1) + 0.2×综合题得分率
单元通过   = 单元内所有 kp 的 mastery ≥ 0.9
"到 90%"   = 目标知识点里 mastery≥0.9 的占比 ≥ 90%
```

### 2.3 用户看到什么（S3 的展开）

**只给**：进度条、当前知识点名、剩余轮次/预估时长、缺口提示。
**绝不给**：本周/今日计划文本、单元划分、课时估算、任何决策理由。

> 用户原话要点："用户不需要看每周要做什么、每天要做什么""指挥官的整体决策和思维是隐藏的"。
> 战术含义：**计划是内部数据结构，进度是外部表现。**

## 3. Agent 制作标准（本白皮书最重要的一章）

> 背景：此前出现过一次严重返工——AI 把"指挥官 agent"写成了「一大段 prompt + 一次 LLM 调用」，被用户判定为不合格。本章就是为杜绝这类退化而写。

### 3.1 一个 agent 的合格结构（缺一不可）

```
backend/agents/<name>/
├── schema.py        # 输入/输出 Pydantic 契约，字段带 description + 长度约束
├── prompts.py       # 只为该 agent 服务；禁止夹带别的 agent 的职责
├── checks.py        # 确定性校验（不调 LLM）；返回问题清单用于修复环
├── variants.py      # V1~V4 四版实现（或按架构需要的最少两版）
├── cases.jsonl      # 评测用例 ≥6 条（含边界/异常）
├── graph.py         # 若该 agent 有内部流程：状态机/节点编排（LangGraph）
└── test_contract.py # pytest 契约测试 ≥8 条，离线可跑
```

### 3.2 禁止清单（出现任意一条即为不合格）

| # | 禁止 | 为什么 |
|---|---|---|
| F1 | **纯 prompt + 单次 LLM 调用**冒充 agent | 没有门禁、没有记忆、没有闭环，不可验收 |
| F2 | 一个文件塞几百行 prompt 字符串 | 无法维护、无法评测、无法定位问题 |
| F3 | 没有 `checks.py` | 输出对错无法自动判定，只能靠人肉看 |
| F4 | 输出不是结构化契约（自由文本） | 下游无法消费，必然污染上下文 |
| F5 | 不接 trace（LangSmith） | 出问题无法回放，等于黑盒 |
| F6 | 让 agent 自己"决定"是否通过 | 判定必须落在确定性证据上（S8） |
| F7 | 把对话历史整段传给下一个 agent | 上下文污染（S5） |
| F8 | 用"临时 thread 用完即丢"实现无记忆 | 无记忆 = 不挂 checkpointer 的纯函数 |

### 3.3 正确写法（判分 agent 为例，示范"结构化 + 门禁"）

```python
# schema.py
class JudgeIn(BaseModel):
    quiz: QuizItem
    answer: str = Field(..., max_length=500)
class Verdict(BaseModel):
    correct: bool
    matched_rule: Literal["exact", "numeric", "symbolic", "llm_fallback"]
    evidence: str = Field(..., description="判定依据，必须可回放")

# checks.py —— 确定性，不调 LLM
def check_verdict(v: Verdict, req: JudgeIn) -> list[str]:
    issues = []
    if v.matched_rule == "llm_fallback" and not v.evidence:
        issues.append("llm_fallback 必须给出 evidence")
    return issues

# graph.py —— 有内部流程的 agent 要用图，不是一次调用
g = StateGraph(JudgeState)
g.add_node("normalize", normalize)   # 归一化（符号/全半角/LaTeX）
g.add_node("compare", compare)       # 数值/符号等价（sympy）
g.add_node("fallback", llm_judge)    # 只有前两步不确定才调 LLM
```

### 3.4 每个 agent 的上下文边界（写死在组装函数里）

| agent | 能进 prompt 的 | 字符上限 | 绝不看 |
|---|---|---|---|
| commander | 只有 id/状态/计数（无自然语言） | 无文本 | 讲解正文、题目正文、学生原话 |
| teach | 1 个知识点包（L2+L3 要点）+ 近 3 轮 | ≤4000 | 别的单元、全局进度 |
| quiz | 讲解摘要（≤300 字）+ 题库候选 ≤6 道 | ≤2500 | 学生历史、其他单元 |
| judge | 题干 + 标准答案 + 学生答案 | ≤1500 | 讲解、历史 |
| sideqa | 支线问题 + 当前 kp 一句话 | ≤1200 | 主干对话全文 |
| exam | 单元 kp 集合 + 题量/难度要求 | ≤3000 | 单轮对话 |

### 3.5 变体与评测（S9 的展开）

每个关键 agent 至少两版，重要 agent 四版：**共用同一份 schema 与 checks**，只在策略上不同。

| 版本 | 主讲 agent 的策略 |
|---|---|
| V1 | 单点直讲（基线） |
| V2 | 打包 + 前置激活 |
| V3 | 打包 + 苏格拉底追问 |
| V4 | 打包 + 苏格拉底 + 自检（术语/要点/覆盖） |

评测铁律：**同一套用例、同一套指标、同一个学生标准**才可比。换了一边就必须重跑基线（此前踩过：v3 收紧了学生标准，导致与 v2 不可比）。

## 4. 角色规格（逐个 agent）

| 角色 | 唯一职责 | 输入 | 输出 | 失败模式（要重点防） |
|---|---|---|---|---|
| `commander` | 管进度、派活、打勾 | 知识树 + 学生状态 + 题库索引 | `Task` | 变成"会说话的规划师"→ 产出大段计划文本 |
| `teach` | 讲透一个知识点包 + 报覆盖 | 知识点包 + 近 3 轮 | `TeachingTurn` + `KpCovered` | 术语不解释；一次塞 5 个新概念 |
| `quiz` | 出原题/变式 | kp + 讲解摘要 + 题库候选 | `QuizItem` | 编题（题库里没有却说"改编自例题"） |
| `judge` | 确定性判分 | 题 + 答案 | `Verdict` | 把判定交给 LLM 自由裁量 |
| `sideqa` | 支线答疑 + 归档 | 支线问题 + kp 一句话 | `SideAnswer` + `ArchiveCard` | 支线内容回流污染主干 |
| `exam` | 单元综合卷 | 单元 kp 集合 | `Paper` | 超纲/难度失真 |
| `arbiter` | 门禁/仲裁/熔断（只这三件） | 各 agent 产出 | 放行/驳回 | 变成第二个"什么都管的指挥官" |

**协同铁律（S6）**：能力节点之间**永不直连**；跨 agent 信息必经 hub 与 `contracts.py`。

## 5. 上下文隔离与无污染（S5 的展开）

### 5.1 三层隔离

| 层 | 做法 | 判据 |
|---|---|---|
| 类型层 | `CommanderState` 里没有能装自然语言正文的字段 | 只有 id / 枚举 / 计数 |
| 组装层 | 每个 agent 一个组装函数，字段白名单写死 | 多余信息物理上传不进去 |
| 长度层 | 见 3.4 的字符上限 | 超限即裁剪 |

### 5.2 记忆分层

| 记忆 | 载体 | 生命周期 |
|---|---|---|
| 会话 | checkpointer（SQLite，`thread_id`） | 一次辅导 |
| 学生画像 | Store / `student` 表 | 跨会话，**绝不进 checkpoint** |
| 本轮工作区 | State | 一次 run |
| agent 私有草稿 | private channel | 不进 stream、不回传 |

### 5.3 明确禁止

- 把对话历史整段复制给下一个 agent
- 子 agent 继承父 agent 全部上下文（除显式 `fork`）
- 用"临时 thread"模拟无记忆

## 6. 2026 技术架构基线（S7 的展开）

### 6.0 现状核查（2026-11，已实测）

| 组件 | 采用版本 | 依据 |
|---|---|---|
| LangGraph | 1.2.x（1.0 已 GA，承诺 2.0 前不破坏） | 图/检查点/HITL/interrupt 是刚需 |
| 检查点 | SQLite（`langgraph-checkpoint-sqlite` 3.x） | 本地零运维；生产换 Postgres |
| 追踪 | LangSmith（`wrap_openai` + `@traceable`） | 已接入验证，12 条 trace 已上报 |
| 模型 | DeepSeek V4 Flash（主力）/ Pro（难题） | 成本与 JSON 稳定性 |
| 结构化 | Pydantic v2 + JSON mode + 修复环 | 契约即接口 |
| 判分 | 确定性（字符串/数值/sympy）＋仅不确定时 LLM 兜底 | S8 |

**已否决**：AutoGen（已归档）、OpenAI Agents SDK handoff（默认共享历史）、CrewAI（控制力弱）、纯 swarm（不可验收）、Temporal（5 周内运维过重）、Dify/Coze 当主流程（承载不了自定义判定）。

### 6.1 权威请求路径

```
学生输入
  └─ commander.pick_next_kp（规则：知识树顺序 + 掌握度 + 权重）
       └─ dispatch_teach（Task：kp + L2/L3 要点 + 题库候选 + 约束）
            └─ teach（LLM）→ 术语门禁（确定性 + 定向修复）→ 讲解
                 └─ dispatch_quiz → quiz 出题 → judge 判分
                      ├─ 未达标 → 回 teach（补强，计次，上限熔断）
                      └─ 达标 → tick_kp（写 Store + 打勾，必须挂判分证据）
                                 └─ progress_update（只推进度条）
```

### 6.2 六道质量门禁（不可省）

| 门禁 | 判据 | 失败处理 |
|---|---|---|
| 知识点不发明 | `kp_id ∈ kp_tree` | 驳回重生成 |
| 要点覆盖 | `points_covered ⊆ 该 kp 的 L2/L3` | 驳回 |
| 原题真实 | `source_problem_id ∈ 题库` | 驳回 |
| 变式挂母题 | `parent_problem_id` 存在 | 驳回 |
| 打勾有证据 | `judge_verdict_ids` 全部可查 | 拒绝打勾 |
| 术语零漏解释 | 讲解中专业名词都有白话解释 | 定向修复一次，仍不合格则驳回 |

## 7. 数据资产战略（S1/S4 的展开）

### 7.1 管线

```
PDF（扫描件 586 页，无文字层）
  └─ MinerU 4.1.7（basic/ONNX 档，30 页一批，失败不阻塞）
       └─ markdown（含 LaTeX 公式）
            └─ 编码修复（UTF-8 被当 GBK：整行 encode('gbk').decode('utf-8')）
                 └─ 知识树抽取（LLM 深度加工，导图白名单约束）
                      ├─ L1：教材导图节点（每讲 5 个左右）
                      ├─ L2：定义/性质/方法/定理
                      ├─ L3：题型/步骤/易错点
                      └─ 结论层：一级结论 / 二级结论
                 每条必须带：页码 + 原文摘录(evidence) + 例题编号
                 └─ 题目库 problems.jsonl（题干/答案/解析/考点/页码/母题）
                 └─ 索引 kp_index.json（kp → 例题/习题 + 缺口标记）
```

### 7.2 实测坑（已写死，不再重踩）

| 坑 | 现象 | 解法 |
|---|---|---|
| Windows 中文路径 | llama.cpp 报 Unicode 错 | 模型放 `C:\mineru_models`，`model.base_dir` 指过去 |
| standard 档崩溃 | VLM 初始化失败 | 降级 `basic`（纯 ONNX），OCR 够用 |
| 中文全乱码 | `鏂扮増` | 整行 GBK→UTF-8 反转修复 |
| 100 页一批崩溃 | 写文件阶段 UTF-8 报错 | 30 页一批，失败跳过 |
| base64 图片撑爆 prompt | 单行几十万字符 | 载入时丢弃 `![](` 行与超长行 |
| 抽取混进结构性标题 | 出现"第1讲/基础知识结构" | **导图白名单强制 L1** |

### 7.3 权重分级（S4 的延伸）

每个 L1 块打 `must / high / edge` + 一句理由；讲解顺序按权重，不按页码。
已实测：第 1 讲按权重排序后，前 10 个知识点依次落在**极限四则运算、洛必达、泰勒、无穷小运算、展开原则、两个重要极限、夹逼、七种未定式**——与考研真实考频一致。

## 8. 主讲 agent 的教学战略

| 要点 | 规定 |
|---|---|
| 打包 | 一次 2–3 个相关知识点（不是一次一个，也不是整讲一口气） |
| 顺序 | 直觉/例子 → 定义 → 算例 → 检查问题 |
| 术语 | 首次出现必须当场解释；上一轮学生说没懂的词，下一轮必须先解释 |
| 自检 | 讲完自报：用了哪些术语、是否都解释过、覆盖哪些要点 |
| 禁止 | 跳过术语、一轮塞超过 3 个新概念、把整讲塞进一轮 |

## 9. 实验与评测协议

### 9.1 指标（唯一口径）

| 指标 | 定义 | 目标 |
|---|---|---|
| `understood_rate` | 学生判"懂"的轮次 / 总轮次 | ≥ 70% |
| `avg_rounds` | 总轮次 / 知识点包数 | ≤ 2.0 |
| `term_leak_rate` | 学生报"没懂的名词"的轮次 / 总轮次 | → 0 |
| `pack_success_rate` | 最终让学生懂的包 / 总包数 | ≥ 90% |
| `grounding_rate` | 引用真实教辅条目 / 总条目 | ≥ 95% |

### 9.2 已实测（第 1 讲前 10 高频点，2026-11-06）

| 数据源 | V1 | V2 | V3 | V4 |
|---|---|---|---|---|
| 旧 prompt（宽松学生）understood | 25% | 14% | 40% | **62%** |
| 术语漏解释率 | 75% | 93% | 60% | 50% |
| 收紧学生标准后 understood | 17% | 15% | 15% | **40%** |

**结论**：V4 稳定最优；"术语零漏解释"靠提示词无法达标 → 必须上**确定性术语门禁 + 定向修复**（已写入 6.2）。

## 10. 界面与体验规范

| 原则 | 做法 |
|---|---|
| 只给进度 | 进度条 + 当前知识点 + 剩余轮次 + 缺口 |
| 不打断学生 | 只在"需要作答""需要确认"时出现交互 |
| 可回溯 | 学生能看到"我这一讲做过哪些题、错在哪" |
| 不炫技 | 不展示 agent 之间的消息、不展示决策理由 |

## 11. 工程与协作规范

| 规范 | 内容 |
|---|---|
| 契约冻结 | `backend/contracts.py` 唯一跨 agent 接口 |

## 12. 过程纪律

1. **动手前先读本文件**，对照 S0–S12。
2. **战术问题自己决定**，不向用户征求 A/B 选择。
3. **战略只增不改**，改必须用户批准（本次 v2.0 为用户指令升级）。
4. **结果导向**：两条迭代无改善即换路径。
5. **验收权在用户**：AI 出证据（指标 + 报告 + trace），用户判"行不行"。
